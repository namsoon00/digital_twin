# 가설과 판단의 사후 검증

## 목적과 범위

새 가설을 제안하는 것으로 끝내지 않고, 검증에 필요한 자료가 부족하면 다시 확인하고, 당시 판단 이후의 실제 관측 결과를 다음 판단에 전달합니다. 이번 변경은 기존 TypeDB 추론·가설 검증·AI 판단·발송 정책을 연결하고 복구 경로를 보완합니다. 별도의 Python 매매 규칙이나 점수를 추가하지 않습니다.

전체 흐름은 다음과 같습니다.

```text
검증된 사실 / 기존 판단의 문제
  -> 가설 제안 병합 (Model Registry)
  -> 선별 -> 후보 규칙 생성 -> TypeDB 검증 / 과거 재현
       관측 자료 부족 / 연결 오류 -> 영속 재시도 -> 같은 가설 재검증
       모델·명세·수집기 미지원 -> 개발 검토 -> 수정 후 명시적 재검증
       검증 통과 -> 운영 반영 승인 대기
  -> 승인된 규칙 + 시점이 고정된 ABox -> TypeDB 근거와 경쟁 가설
  -> 이전 판단의 관측 기록을 한 번 캡처 -> AI 판단
  -> 판단 저장 -> 기존 발송 정책 -> 알림 또는 발송 보류
  -> 사전에 등록한 기간·조건·비교 지수에 따른 관측
  -> 결과 / 자료 부족 / 평가 제외 구분
  -> 다음 AI 판단의 기억과 웹 상세, 개선 제안
```

규칙 생성·구조 검증 성공은 투자 성과 검증 성공이 아닙니다. 새로운 운영 규칙은 기존 승인·배포 절차를 유지합니다. 관측 횟수를 독립 실험 수 또는 예측 성공률로 표시하지 않습니다.

## 자료 부족 가설의 재시도

- `needs-data`는 후보 규칙이 아직 없는 **생성 단계**도 재시도 대상입니다.
- `retry`에 시도 횟수, 마지막 시각, 입력 지문, 다음 정기 확인 시각, 요구 자료, 상태를 저장합니다. 워커 재시작으로 이력이 초기화되지 않습니다.
- 새 입력이 확인돼도 기본 최소 간격 15분을 둡니다. 입력이 같으면 기본 180분마다 재확인합니다. `hypothesisDevelopmentChangedRetryMinutes`와 `hypothesisDevelopmentUnchangedRetryMinutes` 설정으로 조정합니다.
- `next_check_at`과 `last_checked_at`을 JSON과 같은 트랜잭션으로 저장합니다. 상태·재확인 시각 인덱스로 지금 처리할 수 있는 케이스부터 조회하므로, 미래 예약 수십 건이 첫 페이지를 차지해 실행 가능한 가설을 가리지 않습니다. 이전 기록은 첫 확인에서 예약 열을 채웁니다.
- 계정·종목별 가설의 병합과 처리는 같은 MySQL 이름 기반 잠금으로 중복 실행을 막습니다. 다른 워커가 처리 중이거나 아직 재시도 시각 전인 항목은 배치 실행 개수를 소비하지 않습니다.
- 처리 중인 제안은 원본 제안 저장소에 남으며 다음 backlog 확인에서 병합합니다. 완료·폐기·승인 대기·배포 상태는 자동 재실행하지 않습니다.
- 연결·AI 호출 실패는 `dependency-error`, 규칙 구조 오류는 `development-required`로 구분합니다. AI 오류를 빈 후보 목록으로 숨기지 않습니다. 웹 실험실에서 차단 원인 종류, 요구 자료, 마지막 시도, 다음 정기 확인을 볼 수 있습니다.

### 규칙 생성 입력과 대기 원인

`hypothesis-rule-design-v4`는 현재 저장된 규칙의 실제 조건·도출 필드, 필터, 모델·가설 계약을 완전한 예시로 최대 3개 전달합니다. 예시 본문은 합계 20KB 이내이며, 조건을 잘라 의미를 바꾸지 않고 큰 예시 전체를 제외합니다. 규칙 스냅샷 ID와 해시, 계정의 world ID, 대상 종목도 전달합니다. 단순히 조건 개수만 보고 AI가 형식을 추측하지 않도록 하기 위한 변경입니다.

예시는 원본 근거의 규칙 참조와 가설 제목·주장의 관련 용어로 선택합니다. 등록 순서의 처음 30개만 보여주지 않습니다. 이 검색은 작성 자료를 선택하는 것이며 투자 점수나 매매 규칙 선택이 아닙니다. 이전 AI 작성에서 선택한 예시와 재시도 오류 문장은 다음 검색의 근거로 사용하지 않습니다.

별도로 등록 규칙 ID 목록과 관련 계약의 색인을 전달합니다. 색인은 최대 16개 계약 설명, 설명 합계 12KB, ID 목록 12KB로 제한하고 생략 개수와 범위를 명시합니다. 예시에 없는 기능을 미구현으로 단정하지 않습니다. JSON은 공백을 줄여 전달하지만 조건·계약을 임의로 잘라 의미를 바꾸지는 않습니다.

예시는 문법 자료이지 현재 ABox에 그 사실이 있다는 증명이 아닙니다. 근거 ID는 출처 연결이며, 후보 작성을 위해 별도 계보 관계가 반드시 수집되어야 한다고 요구하지 않습니다. 새 예측 주장은 정확한 기존 모델·관측 계약이 있어야 하며 다른 모델로 바꿔 끼우거나 맥락 규칙으로 위장해 검증을 통과시킬 수 없습니다.

후보 명세 생성은 저장된 원본 제안·추론 세대 ID와 규칙 문법으로 수행합니다. 이 단계에서 최신 상세 InferenceBox를 다시 읽지 않습니다. 입력에 `deferred-validation`, `authoring-only`를 명시하며 현재 관계가 0개라거나 검증됐다고 표시하지 않습니다. 실행 가능한 후보가 나온 뒤에는 기존 TypeDB 후보 실행, 현재 ABox 일치, 관측 범위·정책 검증을 모두 수행합니다. 따라서 명세를 만들기 전의 느린 상세 조회는 제거하지만 실제 검증을 생략하지 않습니다.

현재 ABox를 조회하지 않았으면 `observationState=not-queried`입니다. 빈 관계 배열은 결측 증거가 아닙니다. 이 상태에서 AI가 결측·오래된 자료라고 응답하면 `unverified-observation`으로 기록해 검토하도록 합니다. 현재 사실의 존재를 단정하지 않고도 명세와 정확한 모델 계약으로 후보를 작성할 수 있으며, 실제 일치는 후속 TypeDB 검증에서 확인합니다. 후보 규칙과 명시적 차단 사유가 함께 반환된 경우 차단 사유를 무시하고 승인 검증으로 진행하지 않습니다.

관련 규칙 최대 8개에 대해 최대 3개 모델 릴리스의 **저장된 평가 결과**를 계정·종목 범위로 조회합니다. 평가 ID, 모델 릴리스, 원본 feature snapshot, 평가 시각, 충족·미충족·확인 불가 조건 ID를 보존합니다. 모델 평가 본문은 합계 12KB이며 큰 평가 전체를 생략하고 생략 개수를 표시합니다. 다른 종목의 평가를 함께 전달하지 않으며, 계정·모델 릴리스가 다르면 사용하지 않습니다. `not-supported`는 모델이 실행됐지만 조건을 만족하지 않았다는 뜻이지 모델 미등록이나 원천 자료 전체 결측이라는 뜻이 아닙니다.

이 평가 결과는 작성 참고 자료입니다. 과거 제안 시점의 사실로 소급하거나 현재 TypeDB 세대와 동일하다고 간주하지 않습니다. 규칙 스냅샷·예시 ID·조회 상태와 모델 평가 영수증은 AI 호출 **전에** `retry.compilationContext`와 개발 이벤트에 저장하므로 AI 호출이 실패해도 입력을 추적할 수 있습니다. 실패 단계도 명세 생성(`compilation`)으로 남습니다. 웹 검증 게이트의 **저장된 모델 평가**에서 당시 기준 시각과 조건 충족 상태를 확인합니다.

웹의 `투자모델 관리 > 검증 게이트`에서 가설 목록, 차단 이유, 예약 시각을 확인할 수 있습니다. 개발 검토와 관측 대기를 구분하며 승인 조건이 충족되지 않으면 운영 반영 버튼은 비활성화됩니다.

| 차단 종류 | 처리 |
| --- | --- |
| 관측값 없음 / 오래된 관측값 | 수집 자료 재확인 |
| 관측 기간 부족 | 정기 재검증, 기간을 임의로 단축하지 않음 |
| 조회하지 않은 자료를 결측으로 주장 | 확인되지 않은 AI 요구사항으로 구분, 개발 검토 |
| 연결·실행 오류 | 제한된 간격으로 재시도 |
| 규칙 명세 불일치 / 모델·공급자 기능 미지원 | 자동 반복 중단, 개발 검토 |
| 분류되지 않은 기존 자유문장 | 자료 부족으로 추측하지 않고 개발 검토 |

새 응답의 구조화된 `blockers`를 원본으로 사용하고, `requiresData`는 이전 형식의 표시용 목록으로 취급합니다. 같은 요구사항을 짧게 다시 쓴 문장을 별도 미분류 문제로 추가하지 않습니다. 구조화된 항목이 없는 기존 응답만 자유문장 검토 경로를 사용합니다.

### 후보 작성과 후속 검증 분리

v4 응답은 명세 자체를 작성할 수 없는 사유만 `blockers`에 넣습니다. 현재 관계가 맞는지 확인하거나 미래 결과를 기다리는 요구는 `validationRequirements`에 넣고 작성 가능한 후보를 반환합니다. 이전 자유문장을 키워드로 분류해 임의로 차단 해제하지 않습니다.

- `typedb-execution`: 같은 계정 world, 종목, 후보 ID의 읽기 전용 TypeDB 실행 증명으로 확인합니다. 형식 검사만 했거나 일부 규칙 실행을 생략한 `status=ok`는 통과가 아닙니다.
- `current-match`: 위 실행 증명이 있고 모든 후보 조건이 일치해야 통과합니다. 정상 실행의 0건은 `condition-not-met`이며 `missing-observation`으로 표현하지 않습니다.
- `review`: 독립 사건 결과, 미래 구간, 연구 교차검증 등 별도의 증명이 필요한 조건입니다. 실행하지 않은 검증은 `not-run`으로 남고 승인 대기를 열지 않습니다. 현재 일치나 시세 스냅샷 개수로 이 조건을 자동 통과시키는 검증기는 이번 변경에 포함하지 않습니다.

정규화한 응답은 구조 검증이나 실험 생성 **전에** `compilationDraft`에 저장합니다. 원본 후보가 구조 오류로 거부돼도 가능한 초안과 오류를 보존합니다. 저장 범위는 후보 최대 3개, 합계 128KB이며 운영 규칙으로 쓰지 않습니다.

재시도는 가설·근거·반증 조건·작성 계약 버전·world·운영 규칙 스냅샷/해시가 같고 저장 지문이 검증된 후보만 재사용합니다. TypeDB 일시 실패나 실험 저장 실패는 AI 재호출 없이 같은 후보로 이어집니다. 의미 검증에서 거부된 초안은 보존하되 재사용하지 않습니다. 새 후보 내용이나 검증 계획에는 새 실험 ID를 부여해 이전 후보의 검증 결과와 섞이지 않게 합니다.

제안 후 관측의 기준은 오래된 원본 제안 시각이 아니라 **현재 후보 저장 시각**입니다. 이 범위 검사 역시 독립된 사건 결과 검증이나 수익성 검증이 아닙니다. `waiting-condition`은 조건 불성립, `waiting-validation`은 아직 실행하지 않은 후속 검증 요구를 포함한 대기입니다. API의 후보 기록·검증 게이트와 기존 검증 화면에서 같은 케이스를 추적합니다.

모든 후보에 `HOLD`를 강제로 넣지 않습니다. 비예측 참고 관계는 투자 행동 없이 읽기 전용 검증할 수 있지만, `causal-hypothesis` 게이트가 원래 인과 가설의 예측 모델·결과 계약을 요구합니다. 참고 관계가 현재 일치해도 이 게이트는 차단 상태이며 승인·배포·투자 알림으로 넘어가지 않습니다. 원래 인과 주장을 약한 참고 규칙으로 대체해 통과시키는 경로는 없습니다.

후보 조건 확인은 `includeBaseline=false`로 이전 InferenceBox 전체와의 비교 조회를 생략합니다. 이 비교는 진단용이며, 현재 계정 ABox의 존재·준비 상태 확인과 실제 TypeQL 후보 실행은 그대로 수행합니다. 생략한 비교의 상태는 `not-requested`, 이전 개수와 차이는 `null`입니다. 정책 전용 비교와 이 옵션을 지정하지 않은 호출은 기존 비교 경로를 유지합니다.

시세 이력은 저장소의 종목별 사전 형식과 이전 목록 형식을 모두 읽습니다. 계정 범위를 확인하고 관측 시각으로 최신 자료를 고르며, 저장된 `current_price` 등과 API의 `currentPrice` 등을 같은 지문 필드로 정규화합니다. 원본 자료는 바꾸지 않습니다. 관측 이력이 있다는 사실과 가설이 검증됐다는 결론은 별개입니다.

### 같은 실사례의 재실행 결과

2026-09-12 UTC에 SK하이닉스 공시 충격 흡수 가설 한 건을 같은 저장 후보로 추적했습니다. 후보 저장 후 AI 작성 서비스를 사용하지 않고 TypeDB 검증을 재개할 수 있었습니다. 실제 후보 1개를 실행했고 생략은 0개, 현재 일치는 0개였습니다. 이는 DB 오류가 아니라 현재 조건 불성립입니다.

같은 후보 쿼리의 전체 검증 시간은 진단용 이전 InferenceBox 비교를 포함했을 때 121.68초, 제외했을 때 13.62초였습니다. 첫 실행에서 약 96초가 비교 조회와 재시도에 쓰였고 후보 쿼리 자체는 약 4.6초였습니다. 이는 해당 실사례의 측정값이며 모든 종목의 지연 보장은 아닙니다.

저장 이력의 사전 형식을 지원한 뒤 같은 후보를 한 번 더 실행했을 때는 11.83초였고 실제 관측 2건을 읽었습니다. 후보 작성 후 관측 범위는 통과했지만 과거 자료 최소 3건 조건은 충족하지 못했습니다. 최소 보존 정책은 기본적으로 계정 스냅샷 2개를 남기므로 이 과거 자료 조건을 단순 대기만으로 해결할 수 있다고 보장하지 않습니다. 원시 스냅샷 보존량을 늘리거나 검증 기준을 낮추지 않았습니다. 장기 가설 검증은 독립 사건의 시점별 결과를 따로 보존하는 검증 경로가 필요합니다.

생성된 후보는 공시의 인과 효과를 입증하는 예측 모델이 아니라 기존 모델 결과를 연결하는 참고 관계였습니다. 따라서 `causal-hypothesis`에서 차단했고 독립 사건 결과와 연구 교차검증도 `not-run`으로 남겼습니다. 승인·배포·투자 알림은 생성하지 않았습니다. 관측을 더 모으는 것만으로 이 계약 부족이 해결되지는 않으며 원래 주장을 검증할 예측 모델과 결과 검증이 별도로 필요합니다.

### 가설 한 건을 실데이터로 확인할 때

1. 해당 계정의 현재 보유·관심 범위와 원본 개발 케이스를 확인합니다.
2. 운영 규칙 스냅샷에서 관련 등록 모델 계약을 확인하고 같은 종목의 저장된 모델 평가를 읽습니다.
3. 같은 규칙·종목·world로 TypeDB direct TypeQL 조회를 실행합니다. 읽기 전용 검증은 운영 RuleBox·InferenceBox를 변경하지 않습니다.
4. `status=ok, matchedCount=0`은 조회 성공과 조건 미성립을 뜻합니다. 이것만으로 데이터 누락, 모델 오류 또는 미래 예측의 반증을 선언하지 않습니다.
5. 신규 가설이 기존 계약보다 강한 인과 주장을 요구하면 별도 모델·관측 계약을 설계합니다. 유사한 기존 모델을 새 주장의 검증 결과로 바꾸지 않습니다.
6. 실제로 성립하고 적격한 가설만 기존 TypeDB 판단·AI·발송 경로로 보냅니다. 미성립 가설로 투자 알림을 강제하거나 미래 성과를 검증 완료로 표시하지 않습니다.

v3 단계의 이전 실데이터 확인(2026-09-12)에서는 운영 규칙 122개를 읽고, 선택한 등록 가설 하나를 해당 종목과 world로 조회했습니다. TypeDB 조회는 성공했으나 일치 결과는 0개였고, 저장된 모델 평가도 `not-supported`였습니다. 설계 AI는 120초에서 반복 중단됐지만 300초 한도로 실행하자 약 247초에 후보 응답을 반환했습니다. 응답에는 현재 관계 확인과 사건 이후 관측 검증을 요구하는 미분류 항목이 남아 `needs-revision`으로 보존했습니다. 이후 v4에서 같은 케이스를 재개한 결과는 위의 실사례 재실행 절에 기록했습니다. 어느 결과도 신규 가설 승인·운영 배포·투자 알림 발송·미래 성과 검증의 완료를 뜻하지 않습니다.

후보 규칙이 없는 단계에서는 가격만 달라졌다고 다시 AI를 호출하지 않습니다. 새 근거 ID·요구 자료·이력 범위 변화와 최소 간격을 확인하고, 변하지 않아도 정기적으로 재확인합니다. 개발 검토 항목은 기능·명세를 고친 뒤 웹의 `검증 다시 실행`으로 재평가합니다. 모든 자료 도착 이벤트가 해당 가설을 즉시 깨우는 세밀한 의존성 예약까지 구현된 것은 아닙니다.

### 실시간 처리와 개발 검증의 우선순위

실시간 추론이 밀리면 기존처럼 실험실 배치를 양보합니다. 다만 실행 가능한 가설이 기본 30분 이상 기다렸다면 한 번의 워커 주기에 **가설 한 건만** 처리할 기회를 줍니다. `hypothesisDevelopmentMaximumQueueYieldMinutes`로 조정하며 최소 15분입니다. 전체 실험 배치나 새 제안 생성을 함께 실행하지 않습니다.

이는 기존 직렬 워커의 장기 양보를 제한하는 장치이며, 무제한 동시 실행이나 처리 시간 보장은 아닙니다. TypeDB 실행 잠금·정책·승인 조건은 유지됩니다. 단일 외부 호출 자체가 지연되는 경우에는 해당 호출의 복구도 필요합니다.

이 재시도는 기존 자료 수집과 후보 생성 서비스를 다시 호출합니다. 공급자가 제공하지 않는 자료를 새로 만들어 내거나 모든 요구 자료의 수집기를 자동 생성하지 않습니다.

RuleBox 명세를 설계하는 백그라운드 AI의 기본 실행 한도는 300초입니다(`ontologyRuleCandidateAiTimeoutSeconds`, `ONTOLOGY_RULE_CANDIDATE_AI_TIMEOUT_SECONDS`). 실시간 투자 판단·알림의 한도와 독립적이며 명시적 설정이 우선합니다. 모델·반증·정책 계약까지 설계하는 작업이 기존 120초에서 반복 종료되는 경우를 다룹니다. 입력 축소, 동시 실행 슬롯, 투자 판단용 예약 슬롯, 가설별 잠금과 영속 재시도는 그대로 유지합니다. 시간 한도 확대는 생성 성공이나 투자 성과의 보장이 아닙니다.

## 관측과 복구

### 판단 시점의 기준값 보존

관측 시점이 오기 전부터 예약된 종목과 비교 지수를 수집 대상으로 읽습니다. 대상 종목과 비교 지수의 판단 시점 이전 관측값을 찾아 예약의 `baselineObservations`에 가격·출처·시각만 한 번 저장합니다. 판단 이후 시세로 과거 기준가를 대신하지 않습니다.

예약을 다시 저장해도 이 기준값은 유지됩니다. 원시 데이터 보관을 늘리는 방식이 아니며, 하루 단위 원시 시세 정리와 별개로 검증에 필요한 작은 기준값만 보존합니다.

### 자료가 늦게 들어온 경우

`excluded-contract-data-gap`, `excluded-criterion-data-gap` 결과의 예약은 `needs-data`로 둡니다. 마지막 평가 후 15분이 지나면 재확인할 수 있고, 기존 `observed` 결과 중 같은 자료 부족 상태도 조회합니다.

재평가 시 다음 항목은 변경할 수 없습니다.

- 원래 판단 ID와 관측 시각
- 원래 관측 가격과 판단 기준 가격
- 계약 지문과 관측 기간

저장된 `observationFacts`와 해당 시점의 이력만 사용합니다. 이후 현재가로 과거 결과를 보충하지 않습니다. 이미 평가가 완료된 결과는 같은 ID의 재요청으로 덮어쓰지 않습니다. 보충 전 상태는 최근 5회 평가 이력으로 남습니다. 거래가 없었던 시점이나 보관 기한이 지난 자료를 복구할 수 없으면 자료 부족 상태를 유지합니다.

비교 지수가 없으면 사용자/AI용 성과 JSON에서 비교 수익률과 초과 수익률을 `null`로 표시합니다. 기존 SQL 숫자 열의 호환용 0은 실제 관측치가 아니므로 `missingData`와 정규화된 JSON을 함께 사용해야 합니다.

## AI와 웹에서 같은 기록 사용

`DecisionContinuityPacket.reviewSummary`는 이전 판단, 검증된 조건 변화, 관측 결과, 다음 조건을 담습니다. 기존 패킷 버전에 추가된 필드이며 과거에 이 필드가 없는 기록을 최신 시세로 재작성하지 않습니다.

| 상태 | 의미 |
| --- | --- |
| `evaluated` | 정해진 평가에 사용할 수 있는 결과. 그 자체가 투자 성공을 의미하지 않음 |
| `data-gap` | 필수 자료 부족으로 판단 보류 |
| `excluded` | 지연 관측, 불완전 계약, 과거 적격성 미기록 등 평가 대상 제외 |
| `pending` | 연결된 이전 판단이 있지만 아직 결과 관측 대기 |
| `not-recorded` | 연결된 이전 판단 기록 없음 |
| `partial` | 여러 결과가 서로 다른 상태 |

`transitionVerified`와 전이 시각이 없는 후속 조건은 새로 성립한 변화로 보여주지 않습니다. AI 입력 압축 시에도 평가 적격성과 자료 부족을 보존합니다. AI가 관측 결과를 실제 계좌 수익이나 알림을 따라 거래한 성과로 표현하지 않도록 지시합니다.

웹 투자 판단 상세의 **이전 판단과 검증**은 해당 AI 판단이 사용한 패킷을 읽습니다. 이전 판단, 확인된 변화, 사후 검증, 다음 확인을 같은 계정·종목 범위에서 표시합니다. 이후 도착한 결과는 다음 판단의 패킷에 들어가며, 이미 저장된 판단의 설명을 소급 변경하지 않습니다.

회귀 테스트는 재시도 간격·재시작, 중복 실행, 종결 상태, 기준값 보존, 과거 결과 복구, 계정 격리, AI와 웹 기록 일치, 입력 길이 제한을 확인합니다. 트랜잭션 테스트는 운영 DB가 아닌 분리된 테스트 DB를 사용합니다. 브라우저 검증은 데스크톱·모바일의 테스트 데이터를 사용합니다.

실제 운영 상태는 읽기 전용으로 점검하며, 동작 검증에는 승인된 범위에서 기존 가설의 재검증 경로를 실행합니다. 운영 규칙을 자동 승인하거나 가짜 관측을 넣지 않습니다. 기존 자료 부족 가설이 재검증 대상에 들어가는 것은 확인할 수 있지만, 향후 관측 기간이 지나지 않은 가설의 예측 성과까지 즉시 검증할 수는 없습니다. 추후 실제 독립 관측 결과가 쌓이면 가설별 지지·반증과 벤치마크 대비 결과를 검토해야 합니다. 기존 불완전 계약이나 제외된 관측을 임의로 적격 결과로 승격하지 않습니다.
