# 온톨로지 자동 진화

## 실행 경로

```text
TypeDB 근거와 설명되지 않은 가설 간 차이
  -> 기존 가설 제안 큐 -> 근거 ID에 묶인 AI 제안
  -> 가설 개발 케이스 -> 후보 명세와 결과 측정 계약
  -> 읽기 전용 TypeDB 실행 검증
  -> 자료 명세: 필요한 지표/기간/주기 + 실제 수집 가능 여부
  -> 변경 계획 고정: 후보 + 기존 릴리스 + 비교 가설 + 자료 명세 + 정책 + 작성 시각
  -> 별도 TypeDB 후보 데이터베이스 / 기존 V2 독립 실행 워커
  -> 첫 예측의 실제 입력 보존 -> 같은 입력의 후보/비교 가설 관측
  -> 실제 미래 결과 장부 -> 시점과 관측 기간이 같은 비교 쌍
  -> 통계 검증 + 실행 건전성 검증
  -> 원자적 운영 전환 -> 별도의 사후 검증 구간 -> 유지 또는 이전 버전 복원
```

`ontology-lab` 워커의 기존 `process_pending` 경로에서 실행한다. 별도 크론이나 전담 상시 AI는 추가하지 않는다. AI는 제안과 명세 작성에 사용하고, 증거 검증·채택·복원은 버전이 고정된 계약으로 수행한다. TypeDB가 투자 가설과 행동 후보를 추론하며 Python의 진화 정책은 **릴리스 채택 여부**만 결정한다. 알림이나 주문을 직접 만들지 않는다.

## 자동화 범위

이번 실행 가능한 변경은 **기존 TBox 어휘와 지원되는 모델 계약을 사용하는 새 조건부 예측 규칙 및 그 파생 관계 추가**다. 가설 작성 AI는 등록된 예측 모델, 비교 가설, 추가 조건을 선택한다. 행동 후보·반증 조건·결과 측정 계약은 선택한 모델에서 그대로 상속하며, 후보 행동을 무조건 HOLD로 바꾸지 않는다. 일반 규칙 편집 경로와 가설 자동 작성 경로는 별개다.

기존 규칙 ID 수정, 삭제, 새로운 원천 수집기, 미등록 모델, 새로운 TypeDB 타입·역할 정의는 자동 실행 대상이 아니다. 필요한 확장을 기록하고 중단한다. 이 제한을 '모든 TBox 구조를 AI가 자유롭게 바꾼다'고 표현하지 않는다. 기존 가설을 개선할 때도 새 버전 ID로 실험하며 원래 버전은 보존한다.

현재 기존 규칙과 결과 계약이 비교 가능해야 한다. AI는 `model_input_contract.comparisonBaselineRuleId`로 비교 대상을 사전 지정한다. 예측 대상, 결과 지표, 관측 기간, 단위·비교 지수·임계치 크기·필수 조건·자료 출처 정책이 호환되지 않으면 자동 채택하지 않는다. 같은 방향의 같은 예측은 동률이지 새 성과가 아니다. 아직 비교 가설이 없는 완전히 새로운 주장, 설명 가치만 있는 관계, 인과성 자체의 입증은 이 비교로 검증하지 못한다.

자동 실험은 `source_kind=stock`에 한정하고, 서버가 `model_input_contract.evolutionScope`에 검증 대상 계정 world와 종목을 고정한다. 이 범위는 일반·인덱스 TypeQL 조회 모두의 필수 조건이다. 한 계정·종목에서 나온 성과를 다른 계정·종목으로 일반화하여 자동 적용하지 않는다.

## 정책과 검증

기본값은 `modules/model_registry/infrastructure/ontology_evolution_policy.json`에 있고 운영 설정 `ontologyEvolutionPolicy`로 교체할 수 있다. 정책 전체와 해시는 실험 계획에 고정된다. AI 출력으로 검증 문턱을 바꿀 수 없다. 현재 운영 설정에서 `shadow` 또는 `disabled`로 전환하면 기존 자동 실험도 신규 운영 반영을 중지한다.

- 독립된 비교 20건, 최소 5개 관측일, 1,440분 단위 구간별 최대 한 건이며 결과 관측 구간도 겹치지 않아야 한다.
- 작성 시점 이후 첫 20개 일별 예측을 결과와 조인하기 전에 고정하고, 계약에서 가장 짧은 공통 관측 기간을 사전 선택한다. 검증은 그 기간의 예측에 한정하며 장기 성과로 일반화하지 않는다. 초기 결과가 지연되거나 빠져도 나중의 좋은 결과로 대체하지 않는다. 중복 사건이나 겹치는 관측이 있으면 충분성 검증을 통과하지 못할 수 있다. 최소 검증 기간조차 관측 한도보다 길면 시작 전에 명세·정책 불일치로 중단한다.
- 후보 적중 비율이 기존보다 최소 5%p 높고, 반증 비율은 35% 이하, 후보 적중 비율의 Wilson 95% 하한은 50% 이상이어야 한다.
- 동률을 제외한 비교의 정확 부호 검정도 통과해야 한다. 유의수준은 최대 작성 시도 3회로 보정한다.
- 최대 작성 3회, 정기 확인 60분, 후보 관측 기간 최대 30일, 한 번에 한 독립 후보 릴리스.
- 이 수치는 초기 운영 정책이지 수익을 보장하는 투자 임계치나 시장에서 입증된 최적값이 아니다.

같은 계정·종목·보존된 원천 입력·시작 시각·관측 기간·종료 시각의 결과만 비교한다. 각 결과의 ABox 식별자, 가설 계약의 내용 지문과 원본 관측 계약 지문을 확인한다. 비교 가설은 기존 릴리스에서 그대로 가져온 규칙이며, 후보 규칙과 **동일한 격리 릴리스의 동일 입력 시점**에서 관측한다. 이는 두 가설의 예측 비교이지 서로 다른 전체 엔진의 성능 비교가 아니다. 전체 엔진 전환에는 별도의 기존 승격 검증도 필요하다. 오래된 가설 버전, 중복 사건, 겹치는 시간대, 결측·지연·판단 불가 결과는 성공으로 세지 않는다. 대기·미지원·자료 부족은 서로 다른 이유로 기록한다. 비교 쌍이 충분하지 않으면 자동 채택하지 않는다.

현재 조회의 조건 성립과 스냅샷 개수는 기술 검증 또는 자료 범위일 뿐이다. `paired-forward-outcomes` 검증이 실제 투자 결과 비교다. 별도 `review` 요구가 남아 있으면 이 비교를 통과해도 자동 채택하지 않는다.

## 격리, 복구, 정체 방지

- 계획은 `hypothesis_development_cases.payload_json.evolution.plan`에 고정하고 진행 상태는 같은 케이스에 저장한다. 변경 기록에는 계획 지문과 검증 요약을 남긴다.
- 기존 릴리스의 저장된 전체 TBox·RuleBox 그래프를 복사하고 새 규칙과 관련 간선만 추가한다. 현재 코드의 기본 카탈로그로 기존 어휘를 재생성하지 않는다.
- 후보 기동과 재기동도 저장된 릴리스 아티팩트를 복원한다. 운영 TypeDB에는 실험 규칙을 덮어쓰지 않는다.
- 실험 릴리스는 저장된 계획 지문과 `ontologyEvolution.state=shadow` 실행 소유권을 갖는다. 워커 관리자와 원천 이벤트 큐가 같은 등록 계약을 읽으므로, 예전 `reasoningEngineV2DeploymentId` 설정값이 운영 버전을 가리켜도 실험을 기동하고 입력을 전달한다. 단순 후보 포인터만으로 복원용 이전 버전을 실행하지 않으며, `adopted`·`rolled-back` 상태는 실험 입력 대상에서 제외한다.
- 이전에 등록만 된 실험을 복구할 때도 정확한 계획·아티팩트·계정·종목을 검증한 뒤 빠진 실행 소유권만 기록한다. 이미 채택되거나 복원된 영수증은 덮어쓰지 않는다. 등록 완료, 첫 입력 처리, 예측 성립, 미래 결과 비교는 서로 다른 완료 단계다.
- 기존 후보 또는 복원용 버전이 사용 중이면 기다린다. 다른 개발 세션의 후보를 빼앗지 않는다.
- 충분한 결과가 나와도 실제 V2 실행·입력 정합성·지연 등의 기존 승격 검증을 통과해야 한다.
- 운영·발송 소유권, 두 릴리스 상태, 채택 영수증을 한 MySQL 트랜잭션으로 전환한다. 기준 버전이 중간에 바뀌면 전환하지 않는다. 전환 후 케이스 저장 전 워커가 종료되어도 영수증으로 복구한다.
- 채택 이후의 새 독립 관측 구간에서 기존 대비 악화와 높은 반증 비율이 함께 확인되거나 실행 계약이 손상되면 이전 버전으로 복원한다. 다른 릴리스로 운영권이 넘어간 뒤에는 과거 실험이 임의 복원하지 않는다.
- 첫 사후 검증 구간을 통과하면 실험을 마치고 후보 슬롯을 비운다. 이전 아티팩트는 남긴다. 이후 개별 가설의 자격 관리는 기존 결과 관측·격리 정책이 담당한다.
- 사후 검증도 최대 관측 기간 안에 끝내지 못하면 이전 버전으로 복원한다. 검증되지 않은 버전이 무기한 운영과 후보 슬롯을 점유하지 않는다. 결과 저장소 장애 중에도 실행 계약 손상에 대한 복원은 별도로 진행한다.
- 후보 관측 기한은 결과 조회와 승격보다 먼저 확인한다. 결과 저장소 장애, 실험 전용 모드, 실행 건전성 대기 때문에 기한을 연장하지 않는다. 후보 종료 자체가 실패하면 다음 주기에 종료를 재시도한다.
- AI 호출 오류를 '새 가설 없음'으로 바꾸지 않는다. 명세 수정은 제한된 횟수만 재시도하고, 같은 후보의 연결 실패는 AI를 다시 부르지 않고 재실행한다.

## 웹과 검증 방법

### 기존 가설의 자동 재검토 복구

- 자동 진화 도입 전에 `needs-revision` 또는 `blocked`로 남은 케이스는 기존 MySQL 장부에서 제한된 묶음으로 찾아 재검토 예약에 한 번 편입한다. `retry.authoringScheduleVersion`으로 재시작 때 중복 편입을 막는다.
- 이미 실험 계획이 있거나 종료된 케이스, 생성 횟수를 소진한 케이스는 복구 대상이 아니다. `mode=disabled`이면 복구하지 않는다. 기존 검증 실패를 성공으로 바꾸거나 과거 결과를 새 실험 결과로 재사용하지 않는다.
- `authoringAttempts`는 AI 호출 전에 저장해 프로세스 오류에도 생성 횟수가 사라지지 않게 한다. 단, 실행 슬롯을 얻지 못해 모델을 시작하지 못한 경우는 `authoring-capacity-unavailable`로 구분하고 생성 횟수를 소비하지 않는다. 기본 5분 뒤 다시 확인하며 `hypothesisDevelopmentCapacityRetryMinutes`로 조정한다.
- 명세 수정 재시도는 기존 정책의 횟수·간격을 유지한다. 다음 예약 시각 전에는 직접 처리 요청이 와도 자동 경로에서 재호출하지 않는다. 강제 수동 실행은 별도다.
- 실시간 작업에 양보하는 주기에도 예약 복구는 한 건 수행한다. 예약 후 오래 기다린 케이스는 기존 가설 개발 예약 슬롯 정책으로 처리한다. 예약 복구는 AI 실행 성공이나 후보 채택을 의미하지 않는다.

### 작성 실패와 중단 작업

- 후보 명세와 작성 차단 사유가 모두 없는 AI 응답은 `invalid-candidate`다. 빈 배열이나 잘못된 응답은 작성 오류이며 '새 가설 없음'이나 관측 자료 부족으로 처리하지 않는다.
- 재시도 프롬프트에는 직전 실패 사유, 실패한 검증 항목과 한 개의 제한된 후보 명세를 전달한다. 전체 실행 그래프와 모델 평가를 반복 복사하지 않는다. 명세를 수정할 수 없는 미지원 모델·공급자·시점 자료는 구체적인 확장 요구로 남긴다.
- 백그라운드 작성의 기본 시간 제한은 0(제한 없음)이다. 명시적인 양수 설정과 프로세스 종료 제어는 유지한다. 투자 AI의 예약 슬롯을 점유하지 않으며, 작성 횟수 제한과 후보 격리·결과 검증 정책도 그대로 적용한다.
- `processing` 상태를 복구할 때는 작업의 MySQL 배타 잠금을 먼저 확보한다. 실제 실행 중인 작업은 잠금을 얻을 수 없으므로 긴 AI 응답을 고아 작업으로 오인하지 않는다. 잠금이 풀린 중단 작업만 즉시 재예약하며, 원래 후보와 작성 횟수를 보존한다. 이미 고정된 진화 계획과 종료 케이스는 이 복구 대상이 아니다.
- 실행 규칙에 `HAS_MODEL_SIGNAL`이 있으면 명시된 신호·모델 릴리스·원본 가설 계약을 우선한다. 규칙 이름에 `risk`가 포함됐다는 이유로 지지 신호를 위험 신호로 다시 분류하지 않는다. 미등록 모델, 잘못된 신호 계열, 불명확한 연결은 계속 차단한다. 기존 원시 규칙의 마이그레이션 안내와 이미 작성된 실행 조건을 구분한다.
- 검증 코드 수정 후 `HypothesisDevelopmentService.revalidate_saved_candidate(case_id)`로 저장 후보를 명시적으로 재검증할 수 있다. 원래 후보 내용 지문, 입력 근거, 계정·종목, RuleBox 릴리스가 동일하고 구조 검증을 통과해야 한다. 이전 실패 이유를 감사 기록에 남기며 작성 횟수를 초기화하거나 AI를 다시 호출하지 않는다. 종료된 케이스·고정된 실험 계획·실제 명세 차단 사유는 이 경로로 우회하지 않는다.
- 관측 명세의 자료형·범위와 예약된 `source-packet` 요건은 TypeDB 실행 전에 검증한다. 원천 패킷 보존은 시스템 소유이며 AI가 다른 기간의 추가 관측으로 다시 정의할 수 없다. 잘못된 관측 명세를 묵인하거나 최신 자료로 치환하지 않고 작성 피드백으로 남긴다.

### 등록 계약 기반 가설 작성

가설 작성 경로는 `registered-hypothesis-design-v1`을 사용한다. 일반 RuleBox 편집 API를 대체하지 않으며, AI 가설 개발에만 적용한다.

- AI는 `modelRuleId`, `comparisonRuleId`, 추가 조건의 `conditionRefs`, 필요한 추가 과거 관측, 아직 검증할 수 없는 주장을 작성한다. 사용 가능한 모델과 조건은 실제 로드한 릴리스의 카탈로그에서 제공한다.
- 시스템은 선택 모델의 정확한 모델 신호, 결과 지표·기간·임계치, 행동 경계와 자격 정책을 상속하고 새 규칙·주장 식별자를 만든다. AI가 실행 규칙 전체나 내부 필드를 작성할 수 없다. 추가 조건의 충족 여부는 여전히 TypeDB에서 판단한다.
- 작성에 사용한 모델과 성과 비교 대상은 별개다. 비교 대상은 같은 측정 계약의 기존 예측 가설이어야 한다. 같은 방향의 동일 예측을 비교하면 동률이며 새 가설의 우월성을 입증하지 못한다. 반대 가설을 선택할 때도 원래 연구 질문과 실제 모델 계약을 따라야 한다.
- 원천 패킷 보존과 미래 결과 관측은 자동으로 구성한다. 추가 과거 관측만 AI의 `additionalObservations`에 받는다. 예약 지표, 미지원 수집 주기·보존 기간 또는 존재하지 않는 조건은 명세 오류로 보존하고 실행하지 않는다.
- 이전 후보의 별도 `review` 요구는 명세 보정으로 삭제할 수 없다. 조건부 예측의 실험 결과는 원래 주장의 더 강한 인과성을 자동 입증하지 않는다.

v6 명세에서 중단된 예측 후보는 `schedule_contract_repair(case_id)`로 **한 번의 추가 보정 시도**를 명시적으로 예약할 수 있다. 원래 입력·후보 지문과 계정 world를 검사하고, 이전 후보·오류·검증 요구·누적 작성 횟수를 보존한다. 최대 3회 작성 기록을 0으로 초기화하지 않는다. 같은 케이스의 보정은 한 번만 가능하며 종료된 케이스·고정 실험 계획·미지원 모델은 이 경로를 사용할 수 없다. AI 슬롯 대기는 작성 횟수를 소모하지 않는다.

미지원 모델·미확인 관측·미분류 개발 요구는 같은 AI 작성을 반복 예약하지 않는다. 웹의 가설 진행 상태에서 명세 수정, 기능 보완, 연결 복구, 조건 성립 대기와 실제 격리 실험 시작 여부를 구분한다. 실험 계획 저장만으로 실험이 실행됐다고 표시하지 않는다.

### 추론에서 AI로 전달된 결과 추적

- `inferenceDispatchDecision.route=HANDOFF_AI`는 전달 의도이며 큐 등록 성공이 아니다. 실제 반환값은 종목 케이스의 `aiHandoffOutcome`과 추론 작업 결과의 `insight_dispatch_outcomes`에 따로 저장한다.
- 큐 등록은 `awaiting-ai`, 같은 의미의 기존 요청 병합은 `coalesced-ai`, 발송 가치 부족 등 분석 생략은 `archived`, 전달 오류는 `failed`로 구분한다. 요청 번호와 구체적인 사유를 남기며 전달 오류는 원래 작업의 재시도 대상으로 유지한다.
- TypeDB가 행동 권한 없이 검토만 허용한 경우 일반 투자 판단 기본값보다 `context-narrative` 계약을 우선한다. AI는 설명할 수 있지만 `REVIEW_ONLY`를 매수·매도 권한으로 승격시키지 않는다.
- 큐에 등록됐어도 최종 알림 발송은 AI 검증과 기존 중복·쿨다운·발송 가치 판정 뒤에 결정한다. 알림 수를 늘리려고 이 기준을 우회하지 않는다.
- 종목별 원천 보충 조회는 전체 자료를 읽더라도 해당 사건의 `replacementRootScopeIds`만 관계 의미 변경의 소유권을 가진다. 연결 유지용 endpoint companion까지 새 의미의 소유자로 검사하면 다른 종목의 변경 때문에 현재 종목 추론이 막힌다. 실제 갱신 대상의 파생 관계 교체와 최종 endpoint 존재 검사는 계속 적용한다.
- 활성화 제어 쿼리가 원자 트랜잭션 한도를 넘으면 변경 대상 포인터의 삭제만 최대 16개 scope의 합집합 쿼리로 묶는다. world 경계와 scope 목록을 유지하며, 독립 노드를 조인하지 않는다. 묶은 뒤에도 한도를 넘으면 쓰기 전에 중단한다. 활성 포인터와 복구 장부를 여러 커밋으로 나누거나 한도를 자동 확대하지 않는다.

실험실의 가설 개발 상세에서 격리 관측, 독립 비교 수, 새 가설만 맞은 수와 기존 가설만 맞은 수, 제외 자료, 기준·후보 버전, 대기 이유, 채택·복원 상태를 조회한다. 웹은 장부를 읽으며 새 투자 추론을 실행하지 않는다.

### 실험에 맞춘 자료 구조

기존 하루치 운영 캐시만으로 장기간의 가설을 검증할 수는 없다. 다음 세 장부를 기존 MySQL 저장 계층에 추가한다. 새 DB나 수집 워커를 만드는 기능은 아니다.

| 장부 | 내용 | 역할 |
| --- | --- | --- |
| `ontology_experiment_observation_plans` | 고정된 실험 계획, 계정·종목·후보 릴리스, 시작/종료/만료 시각 | 어떤 실험을 언제 수집할지 결정 |
| `ontology_experiment_datasets` | 원천 패킷 실제 내용, 요청된 과거 지표 표본, 전체 내용 지문 | 원천 캐시가 지워져도 사용한 입력을 확인 |
| `ontology_experiment_dataset_members` | 첫 관측 시점, 후보/비교 가설, 입력 식별자, 결측 이유, 최종 관측 결과 | 같은 자료의 비교와 첫 예측 고정 |

`model_input_contract.observationRequirements`는 RuleBox 규칙에 저장되는 입력 명세다. 투자 규칙 자체는 계속 TypeDB에서 실행하고, Python은 자료 확보 여부와 실험 보존을 담당한다. 명세는 후보와 비교 가설 양쪽을 합쳐 `evolution.plan.observationRequirements`에 고정한다. 미래 결과의 지표와 관측 기간은 각 가설의 기존 결과 계약에서 가져오며 별도의 성공 기준을 새로 추정하지 않는다.

```json
{
  "observationRequirements": [
    {
      "metric": "price",
      "label": "직전 한 시간 가격 관측",
      "lookbackMinutes": 60,
      "minimumSamples": 12,
      "cadenceSeconds": 300,
      "maximumDelayMinutes": 10
    }
  ]
}
```

- 항상 판단 시점의 원천 패킷 식별자와 내용을 요구한다. 현재 추가 시계열 어댑터는 `price`, `volume`, `profitLossRate`를 지원한다. 이는 원천 패킷에 포함된 뉴스·재무 등 모든 자료를 이 세 지표로 제한한다는 뜻이 아니라, **추가 관측 기간을 직접 검증하는 어댑터의 범위**다.
- 기존 모니터 수집 주기보다 빠른 관측, 1,440분 초과 과거 구간, 미등록 지표는 `unsupported`다. 외국인 장중 주문 취소처럼 원래 수집하지 않은 자료를 AI가 요구했다고 해서 수집기가 생기지 않는다. 해당 공급자와 어댑터를 먼저 구현해야 한다.
- 앞으로 현재 수집기로 채울 수 있는 구간은 `future-collection`, 이미 지나갔고 보존되지 않은 실험 시점은 `historical-unrecoverable`로 구분한다. 결측을 0이나 최신 값으로 대체하지 않는다.
- 가격 등은 공급자의 관측 시각(`source_as_of`)을 사용한다. 같은 시세를 여러 번 조회해도 새 독립 표본이 아니다. 패킷 기록 시각까지 알려진 표본만 사용하고 이후 수정·역사 보충 자료는 과거 입력에 넣지 않는다. 통화가 다른 가격을 한 시계열로 잇지 않는다.
- 필요한 표본 개수뿐 아니라 시작 구간, 마지막 표본 지연, 중간 수집 간격도 확인한다. 최초 관측에 입력이나 비교 가설이 빠지면 그 사실을 남긴다. 뒤의 좋은 결과로 최초 관측을 바꾸지 않는다.
- 후보 릴리스의 첫 예측 저장 트랜잭션 안에서 입력과 두 비교 대상의 연결을 보존한다. 입력이 크거나 복구 불가능하면 그 실험 관측을 부적격으로 남기며 투자 행동이나 발송 권한을 새로 부여하지 않는다.
- 지원 어댑터의 명세는 자료 요건이다. 관측한 모든 원천 값이 경제적으로 정확하다거나 모든 모델 입력이 충족됐음을 대신 보증하지 않는다. 기존 공급자 품질·모델 계약 검증도 그대로 필요하다.

### 보관과 재현 범위

- 원천 운영 이력의 하루 보관 정책은 유지한다. 실험 입력은 별도 수명으로 관리한다.
- 사전 검증과 채택 후 검증 각각 첫 독립 관측 수만큼만 보존한다. 기본 20개 시점씩, 입력 묶음당 최대 2MB다. 같은 시점의 후보와 비교 가설은 한 묶음을 공유한다. 과거 구간에서는 요청한 지표 값만 복사하고 과거 계좌·뉴스 패킷 전체를 매번 보존하지 않는다.
- `experimentEvidenceRetentionDays` 기본값은 종료 후 7일이다. 계획 자체에도 두 관측 기간과 정리 유예를 합친 만료일을 두고, 기존 실험 워커가 만료 행을 최대 500개씩 정리한다. 워커 장애로 종료 처리가 늦어져도 무기한 보관 계약으로 바뀌지 않는다.
- 지원하는 재현 범위는 `source-packets-and-observed-claims`다. 원천 입력, 선택한 표본, 예측 계약, 실제 측정 결과를 재확인할 수 있다. 당시 TypeDB 전체 ABox, 외부 AI 응답 생성 과정과 모든 모델의 내부 상태까지 비트 단위로 재실행하는 기능은 아니다.
- 자료 명세와 보존 입력이 없는 이전 실험은 이 검증으로 자동 승격하지 않는다. 과거 결과에 현재 입력을 붙여 검증된 실험으로 소급 변환하지 않는다.
- 웹의 **실험에 필요한 자료**에서 기간·주기·확보 상태, 보존한 입력 개수, 복구 불가 및 결과 대기, 종료 후 보관 기간을 확인한다. 원본 계좌 자료는 화면이나 알림에 추가 노출하지 않는다.

`test_experiment_observations.py`는 미래 정보 유입, 원천 변조, 계정·종목 혼입, 미지원 지표, 공급자 시각, 수집 간격, 최초 표본 고정, 원천 삭제 후 입력 재조회, 결과 불변성, 자동 정리와 실행 가능 비교 가설의 관측을 검증한다. 실험 데이터 조회 성공은 새 가설의 미래 성능 검증 성공이 아니다.

`test_ontology_evolution.py`는 계획 변조, 예전 결과 재사용, 중복·누락, 동률, 유리한 구간 재선택, 모델 장애, 실험 전용 모드, 미검증 연구 요구, 채택·복원을 검증한다. `npm test`에 포함한다. 실제 DB 조회 성공은 전 구간 실증 성과가 아니다. 새로운 후보의 미래 결과가 아직 없다면 '구현과 실행 검증 완료, 실증 결과 관측 대기'로 구분한다.
